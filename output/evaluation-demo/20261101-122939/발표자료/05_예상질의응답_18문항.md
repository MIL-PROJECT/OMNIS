# 평가위원 예상 질의응답

짧은 답변은 약 30초, 확장 답변은 약 90초 설명을 위한 말하기 원고다. 실제 속도와 추가 질문에 따라 조절한다. ‘확장’은 짧은 답변에 이어 보충하는 방식으로 사용할 수 있다. 기술 주장 수준은 근거표와 일치시킨다.

## 01. 이 시스템의 novelty를 한 문장으로 말한다면?

**짧은 답변 · 약 30초**

새로운 AI 알고리즘보다는 운용 제약에 맞춘 구성의 차별성입니다. 접수와 정비·일일 통제 기록을 연결하고, 외부 추론 실패에 기본 업무가 종속되지 않도록 하며, 사람이 검토해 반영하는 책임 경로를 함께 구현했습니다. 이 구성이 현장 누락과 인수인계에 도움이 되는지는 같은 과업으로 실증해야 합니다.

**확장 답변 · 약 90초용 설명**

평가 관점을 세 층으로 나누겠습니다. 첫째는 업무 연결입니다. 상태를 바꾸는 화면뿐 아니라 완료 결과 조건, 일일 기록 정합성, 다음 근무 초안을 함께 다룹니다. 둘째는 추론 경로의 경계입니다. LOCAL 규칙과 선택 모델을 구분하고 실패하면 실제 어떤 제공자로 실행됐는지 남깁니다. 셋째는 반영 책임입니다. 추천 생성과 업무 변경은 별도 요청이며 Main에서 계정과 조건을 검사합니다. 상태 머신, 역할 통제와 어댑터는 일반 설계 패턴입니다. 따라서 알고리즘 신기술이나 세계 최초로 평가를 요청하지 않습니다. 특정 ITSM·CMMS보다 우수하다는 근거도 없습니다. 제안하는 차별성은 로컬 운용·정비 맥락에 이 원칙을 함께 적용한 구성이고, 가치는 기록 누락률·정합률·인수인계·과업 시간을 기준으로 확인하겠습니다.

## 02. 기존 업무관리 프로그램과 무엇이 다릅니까?

**짧은 답변 · 약 30초**

접수 목록만 관리하는 경우와 비교하면 결과 조건, 정합성, 인수인계와 AI 반영 책임까지 연결한 범위를 보여 드릴 수 있습니다. 다만 특정 상용 제품에 이 기능이 없다고 조사한 것은 아닙니다. 제품 우위보다 해당 업무를 더 적은 누락으로 수행하는지를 평가 기준으로 두었습니다.

**확장 답변 · 약 90초용 설명**

비교의 출발점은 제품 이름이 아니라 과업입니다. 가상 접수의 조치 결과를 기록하고, 다음 근무에 전달하며, 잘못된 추천과 제공자 장애에도 업무 상태를 유지하는 과업을 정의합니다. 기존 방식과 OMNIS에 같은 입력과 종료 조건을 주고 결과를 비교합니다. 과업 시간만 보면 빠른 대신 기록을 빠뜨린 결과가 유리할 수 있으므로 누락과 정합성, 실패율을 같이 봐야 합니다. 기존 제품이 같은 통제를 제공하면 그 기능도 동등하게 사용해야 공정합니다. 현재는 비교 실험 수치가 없으므로 ‘더 빠르다’나 ‘정확하다’고 말하지 않습니다. 현업 요구, 설치 제약, 데이터 이전과 운영 비용까지 포함해야 도입 판단이 가능합니다. 본 발표는 그 실증을 시작할 수 있는 현재 구현과 시험 근거를 보여 드리는 범위입니다.

## 03. 왜 웹 서비스가 아니라 Electron입니까?

**짧은 답변 · 약 30초**

현재 구현은 한 PC에서 로컬 자료를 저장하고 데스크톱 기능을 사용하는 전제를 갖습니다. React UI와 Main 업무 서비스를 분리하면서 별도 웹 서버 없이 동작합니다. 여러 PC의 중앙 동시 업무가 필요해지면 이 선택만으로 충분하지 않으며 중앙 API·인증·동시성 구조를 추가해야 합니다.

**확장 답변 · 약 90초용 설명**

현재 구조의 장점은 UI와 로컬 파일·저장 기능을 하나의 데스크톱 배포 단위로 제공하고 기본 기록이 외부 서버 가용성에 의존하지 않는 점입니다. 반면 Electron 실행 환경의 업데이트, 로컬 자료 보호, 설치·패키징과 OS별 시험 부담이 있습니다. 웹보다 본질적으로 안전하거나 가볍다고 주장하지 않습니다. Renderer의 Node 접근을 막고 contextBridge와 등록된 IPC를 통해 Main이 검사하도록 했습니다. 이 경계는 로컬 실행의 위험을 줄이는 일부 조치이며 완전한 보안 보증은 아닙니다. 중앙 동시 수정이 주요 요구가 되면 업무 서비스를 서버 API로 분리할 수 있지만 세션, 파일, 권한과 오류 경로를 함께 재설계해야 합니다. 현재 단일 PC 요구에 맞는 구현과 이후 전환 비용을 구분해 평가해야 합니다.

근거·화면: 장면 06·07·20 / main/index.ts / C01·C02·C11

## 04. 권한 검사는 UI를 조작하면 우회할 수 없습니까?

**짧은 답변 · 약 30초**

화면에 버튼이 보이는지만으로 허용하지 않습니다. 등록 IPC의 입력 검사 이후 Main에서 현재 계정 상태와 역할, 필요한 업무 조건을 다시 확인합니다. 관리자 E2E에는 직접 IPC 요청으로 관리자 기능을 시도했을 때 거절되는 검사도 포함합니다. 다만 모든 조회가 같은 행 단위 통제를 가진다고 확대하지는 않습니다.

**확장 답변 · 약 90초용 설명**

Renderer는 신뢰 경계 밖의 요청자로 봅니다. nodeIntegration을 끄고 sandbox와 contextIsolation을 사용하며 preload가 제한된 API를 노출합니다. 등록 IPC는 메인 프레임에서 온 요청인지와 Zod 입력 형식을 확인합니다. 인증 서비스는 활성 여부, 잠금, 인증 버전 등 현재 DB 상태를 기준으로 세션을 판단합니다. 서비스마다 역할뿐 아니라 대상과 상태 조건이 필요합니다. 역할 변경이나 잠금 뒤 예전 세션 권한을 그대로 유지하지 않도록 하는 검사가 있습니다. 관리자 민감 변경에는 재인증·사유·동시 수정 확인도 있습니다. 다만 IPC 형식 검사만으로 모든 업무 권한이 보장되지는 않습니다. 새 채널은 권한·대상 범위·오류 응답과 직접 호출 회귀를 함께 추가해야 합니다. OS 관리자나 앱 실행 파일을 바꾸는 공격까지 로컬 앱이 모두 막는다고 설명하지 않습니다.

## 05. AI가 잘못 추천하면 자동으로 업무가 바뀝니까?

**짧은 답변 · 약 30초**

분석과 반영은 분리돼 있습니다. 실제 촬영에서도 분석 후 업무 분류·중요도·정비반 필드가 그대로인 것을 비교했습니다. 권한 있는 담당자가 검토 후 반영을 눌러야 별도 업무 변경 요청이 나갑니다. 잘못된 추천을 줄이는 통계적 성능과 사람의 검토 효과는 추가 평가가 필요합니다.

**확장 답변 · 약 90초용 설명**

추천은 분류, 우선순위, 정비반 후보와 근거를 제시하지만 그것만으로 실제 업무 상태를 변경하지 않습니다. 화면은 별도의 반영 동작을 제공하고 Main의 업무 API가 현재 권한과 조건을 적용합니다. 촬영의 LOCAL 분석 실행은 applied 값이 처음에는 없고 명시적 반영 뒤 적용 이력이 남는 것을 확인했습니다. 이 구조는 인간 검토를 거치는 통제 장치이지 사람이 항상 옳게 판단한다는 보장은 아닙니다. 추천 근거가 설득력 있어 보여 과신할 위험도 있습니다. 따라서 평가에서는 전문가 정답과 추천을 비교하고, 적절하지 않은 추천을 사람이 실제 반영하는 비율을 별도 측정해야 합니다. 기존 상태·대상 조건을 만족하지 않는 추천은 거절하고 누가 왜 반영했는지 추적하는 방향으로 관리합니다. 자동 종결을 수행하는 에이전트로 설명하지 않습니다.

근거·화면: 장면 11·15 / capture.json aiReview / C05

## 06. LOCAL과 Ollama는 같은 로컬 AI입니까?

**짧은 답변 · 약 30초**

둘 다 사용자 PC에서 실행할 수 있지만 구현이 다릅니다. LOCAL은 Main 안의 결정적 규칙이고 생성형 언어모델이 아닙니다. Ollama는 별도 프로세스의 모델 API입니다. 영상은 Ollama 연결 실패 후 LOCAL 규칙으로 복귀하는 장면이며, 생성형 모델이 정답을 낸 장면으로 제시하지 않습니다.

**확장 답변 · 약 90초용 설명**

LOCAL은 외부 추론 연결 없이 동일한 규칙과 입력으로 결과를 만드는 기본 제공자입니다. Ollama는 로컬 모델 서버가 실행되어 있고 해당 모델과 API가 사용 가능해야 합니다. 두 경로를 모두 ‘로컬 AI’라고만 부르면 품질·자원·장애 조건을 혼동할 수 있습니다. 실행 이력에는 선택한 제공자와 실제 제공자를 구분해 표시합니다. 이번 촬영은 미기동 loopback 주소를 선택해 실제 NETWORK_ERROR를 만든 뒤 LOCAL로 복귀했습니다. 기본 고장 저장은 이 모델 연결을 필수로 하지 않습니다. OpenAI·Anthropic은 별도 외부 경로이고 설정·동의·자격정보·전송 조건이 다릅니다. 일반 모델과 Ollama의 의미적 성능은 실제 운용 자료로 별도 검증해야 하며, 이번 규칙 복귀 시험으로 생성형 모델의 정확도까지 입증할 수 없습니다.

근거·화면: 장면 10·14 / 실제 실행 이력 / C04·C08

## 07. AI 신뢰도 78%는 정확도입니까?

**짧은 답변 · 약 30초**

아닙니다. 화면의 confidence는 현재 추천 로직이 반환한 값이며 실측 정확도나 통계적으로 보정된 확률이 아닙니다. 업무별 전문가 정답, 대표 표본과 오류 기준을 마련해 별도로 평가해야 합니다. 이번 자료에는 정확도 개선 수치를 넣지 않았습니다.

**확장 답변 · 약 90초용 설명**

정확도라고 부르려면 무엇이 정답인지, 어떤 표본을 사용했는지부터 정의해야 합니다. 분류, 우선순위, 정비반 추천은 평가 기준과 잘못된 추천의 비용이 다릅니다. 전문가 간 불일치도 기록해야 합니다. 전체 정답률 하나만 제시하면 드문 긴급 사례의 실패가 가려질 수 있으므로 범주별 오류와 누락, 미지원 응답을 함께 확인합니다. confidence를 확률로 사용하려면 예측 값과 실제 정답 비율의 관계를 검증하고 보정해야 합니다. 현재는 그 절차를 수행하지 않았습니다. 사람 검토를 포함하면 추천 타당성과 실제 오반영률을 분리해 봐야 합니다. 이번 영상의 0.78은 합성 사례에 대한 규칙 응답의 수치이지 78%의 현장 성공을 관측한 결과가 아닙니다. 따라서 의사결정 보조 정보와 검증된 성능 주장을 분명히 나누겠습니다.

근거·화면: 장면 11·28 / AI 평가 계획 / C05·C14

## 08. 외부 AI에 민감 자료가 나가는 것을 어떻게 다룹니까?

**짧은 답변 · 약 30초**

현재 외부 경로는 설정과 동의, 입력 최소화와 보호 규칙, 자격정보 저장 경계를 갖습니다. 그러나 패턴 검사로 완전한 비식별화를 보장하지는 않습니다. 이번 촬영은 외부 유료 API를 호출하지 않았고 Ollama loopback 오류와 LOCAL 복귀만 확인했습니다. 실제 허용 자료와 전송 정책은 조직 승인이 필요합니다.

**확장 답변 · 약 90초용 설명**

입력 보호는 기술 규칙과 운영 정책을 함께 봐야 합니다. 현재 ExternalDataGuard와 제공자 설정은 일부 민감 패턴과 전송 조건을 검사하지만 모든 군사·개인·운용상 민감 의미를 이해하는 장치가 아닙니다. 필요한 항목만 보내고 조직에서 허용한 자료를 선택하는 정책이 먼저여야 합니다. 키는 Renderer 업무 DB와 분리해 Main의 safeStorage 경로를 사용하며 운영체제 암호화가 불가능하면 저장을 거절합니다. 이것은 DB 전체 암호화와 다릅니다. 실행 이력의 externalTransmission 역시 프로그램이 관측한 경로 정보이지 패킷 전수 감사의 대체가 아닙니다. 실제 외부 서비스 사용 시 승인 계정, 모델 접근·보존 설정, 망 경로, 전송 최소화와 로그 보존을 검증해야 합니다. 현재 영상은 그런 실제 외부 운영 적합성 판정을 내리지 않습니다.

근거·화면: 장면 09·10·27 / ExternalDataGuard.ts / AISecretStore.ts

## 09. SQLite로 어느 정도 사용자와 데이터를 감당합니까?

**짧은 답변 · 약 30초**

현재 검증 범위에서 동시 사용자 수나 최대 처리량 수치를 제시할 근거는 없습니다. 한 설치 환경의 로컬 DB와 세션이 중심입니다. WAL과 잠금 대기가 있지만 여러 PC가 안전하게 동시 편집하는 서버 구조는 아닙니다. 요구 규모를 정하고 대표 데이터로 읽기·쓰기·복구를 측정해야 합니다.

**확장 답변 · 약 90초용 설명**

확장성은 파일 크기만으로 결정되지 않습니다. 요청 빈도, 조회 범위와 인덱스, 첨부 크기, 백업 중 접근, 동시 수정과 UI 응답을 함께 봐야 합니다. 현재 SQLite 설정은 로컬 접근을 위한 것이며 여러 PC의 공유 폴더에 DB를 놓으면 해결된다고 제안하지 않습니다. 중앙 업무가 필요하면 인증과 API, 트랜잭션, 예상 version에 의한 충돌 처리, 이벤트 전달·오프라인 정책을 정의해야 합니다. 서버형 저장소 선택은 그 뒤의 결정입니다. 기존 Main 업무 규칙을 재사용할 수는 있지만 파일 접근·권한·세션이 로컬 전제이므로 이전 작업이 필요합니다. 기준 부하와 수용 지연, 데이터 손실 허용치와 복구 목표를 사전에 합의하고 시험해야 규모를 답할 수 있습니다. 이번 단위 테스트 97개나 CI 성공을 처리량 보증으로 환산하지 않겠습니다.

## 11. 중복 파일이나 순서가 바뀐 자료를 받으면 어떻게 합니까?

**짧은 답변 · 약 30초**

현재 연동 기능은 미구현이므로 설계안으로 답하겠습니다. 출처·외부 업무 ID·revision·처리 종류를 멱등 키로 제안하고 같은 변경의 중복 효과를 막습니다. 파일 hash는 원본 확인용으로 분리합니다. 낮은 revision이나 같은 키의 다른 내용은 충돌로 보류하는 정책이 필요합니다.

**확장 답변 · 약 90초용 설명**

파일을 다시 받았다는 사실과 업무 변경이 중복이라는 사실은 다릅니다. 같은 업무 변경이 다른 포맷 파일에 들어올 수 있고 한 파일 안에 여러 업무가 들어올 수 있습니다. 따라서 원본 hash와 업무 멱등 키를 별도 관리해야 합니다. 제안은 sourceSystem, externalId, revision, operation 조합에 내용 hash를 대조하는 방식입니다. 같은 키·같은 내용이면 기존 영수증을 반환하고, 같은 키·다른 내용은 자동 덮어쓰지 않습니다. 늦게 도착한 revision과 내부 동시 수정도 별도 충돌로 표시합니다. 승인과 업무 쓰기, 멱등 처리 기록은 논리 트랜잭션으로 묶어 중단 후 재시도에 대응해야 합니다. 전송이 exactly-once라고 가정하지 않고 재전달되어도 효과가 중복되지 않도록 설계합니다. 이는 구현 후 중복·순서 역전·승인 직후 중단 시험으로 확인할 제안입니다.

## 16. 템플릿 변경과 반복 정비는 기존 업무에 어떤 영향을 줍니까?

**확장 답변 · 약 90초용 설명**

양식을 최신 값만 참조하면 과거 기록의 질문 의미가 바뀌거나 점검 항목이 사라져 결과를 해석하기 어려울 수 있습니다. 현재는 업무에 당시 기준을 연결하는 snapshot을 두어 양식 버전 변경과 업무 기록의 책임을 나눕니다. 새 업무는 바뀐 기준을 적용하고 기존 업무는 당시 기준을 유지하는 방향입니다. 반복 정비는 규칙 ID와 occurrence date를 기본 키로 가진 회차 기록을 사용합니다. 예정일을 조정해도 원래 회차 식별을 유지하는 의미가 중요하며, 중복 실행과 규칙 수정의 회귀가 필요합니다. 다만 반복 규칙이 있다고 백그라운드 상주 서비스가 매일 자동 작업을 생성하는 것은 아닙니다. 현재는 미리보기와 생성 요청 경로입니다. 현장에서 자동 생성이 필요하면 실행 주체·중단 복구·중복·승인과 오류 알림을 별도 설계해야 합니다.

정상 접수는 체계가 미지정일 수 있어 system_id가null이 됩니다. Renderer의 분석 요청은 그 값을 systemId에 그대로 넣지만 ai:triageIncident 스키마는 nullable이 아닌 optional string입니다. 따라서 모델 호출 이전 입력 검사에서 오류가 납니다. 이 경우 fallback 성공이라고 해석하면 안 됩니다. 이번 촬영은 오류 증거와 실패 manifest를 보존하고 제품을 고치지 않은 채 체계를 명시한 가상 접수로 다시 진행했습니다. 주된 아키텍처 설명과 실제 LOCAL 복귀 시험은 완료했지만 ‘모든 입력 경로 정상’이라고 말하지 않습니다. 후속 수정은 null과undefined 의미를 계약에 맞춰 정규화하고, 체계 지정·미지정·기존 자료·분석 취소·재분석·반영 조건을 함께 회귀하는 것이 적절합니다. 시험 통과 건수만으로 충분하지 않다는 점을 평가 자료에도 반영했습니다.
