너는 숙련된 Electron/React/TypeScript 개발자이자 업무용 프로그램 구현 파트너다. 기존 OMNIS의 기능과 디자인을 유지하면서 아래 5개 기능을 실제로 구현하고 검증하라.

1. 고장 접수 템플릿
2. 내 업무 모아보기
3. 정비 체크리스트
4. 반복 정비 등록
5. AI 입력 보완 도우미

계획이나 예시 코드만 작성하고 끝내지 않는다. 실제 코드·DB migration·IPC·UI·테스트·실행 가능한 Windows 패키지·사용설명서까지 완성하라. 기능을 복잡하게 확장하기보다 사용자가 바로 이해하고 편하게 쓰게 만든다. 오류·권한·데이터 유실·중복 생성까지 처리하는 것이 완료 기준이다.

## 3. 기능 A: 고장 접수 템플릿

### 사용 흐름

고장관리의 기존 `신규 고장 접수` 화면 상단에 `자주 발생하는 고장` 선택을 넣는다.

기본 합성 템플릿 6개:

1. 인터넷·네트워크 접속 불가
2. 통화 불가·통화 잡음
3. 장비 전원 불량
4. 무선통신 끊김
5. 영상·CCTV 화면 미표시
6. 업무 프로그램 접속 오류

선택하면 제목, 증상 입력 안내, 분류, 서비스 영향 입력 안내, 확인 질문을 미리 보여준다. `빈 항목 채우기`를 기본으로 적용한다. 기존 작성 내용과 충돌하면 변경 미리보기에서 교체할 항목을 사용자가 선택한다.

### 필수 동작

- 템플릿 적용은 접수 저장과 분리한다. 적용 후 모든 일반 업무 필드는 자유롭게 수정할 수 있다.
- 기존 텍스트를 임의로 덮어쓰지 않는다. 템플릿 변경·해제 시 사용자가 쓴 내용과 답변을 보존한다. 적용 직전 상태로 `되돌리기`를 제공하되 이후 사용자 편집까지 잃지 않도록 확인한다.
- 증상 예시는 placeholder/안내 또는 명확히 표시된 예시 미리보기다. 사용자가 확인하지 않은 예시 증상을 실제 발생 사실로 저장하지 않는다.
- 중요도는 예시 문구만으로 자동 긴급 확정하지 않는다. 기존 수동 선택과 AI 검토 후 반영을 유지한다.
- 실제 장비·담당자·신고자·시각을 가짜 값으로 채우지 않는다. `미확인`은 관측 사실과 구분한다.
- 템플릿을 사용하지 않은 기존 자유 접수도 정상 동작한다.
- 질문은 3~5개 이내. 예: 언제부터 발생했는지, 한 장비/여러 장비인지, 표시된 오류, 서비스 영향, 이미 해본 조치.
- 질문의 `필수`는 보완이 필요하다는 안내다. 답을 모르면 `확인하지 못함`을 선택할 수 있고 긴급 접수·기존 접수 경로를 막지 않는다. 기존 계약의 필수 제목·내용 검증은 유지한다.
- 답변은 질문 ID와 구분하여 저장한다. 본문에 반복 이어붙이기하지 않는다. 저장 전 사람이 볼 수 있는 본문/보완정보 미리보기를 제공한다.
- 템플릿 ID·버전·질문 문구와 답변 snapshot을 접수에 연결하여 이후 템플릿 수정이 과거 기록을 바꾸지 않게 한다.
- ADMIN이 기존 시스템관리의 간단한 탭/대화상자에서 템플릿 제목·안내·질문·사용 여부를 관리할 수 있게 한다. 비활성화는 과거 기록을 지우지 않는다. 시스템 ID는 안정적으로 유지하고 사용자 수정 템플릿을 매 실행 seed로 덮어쓰지 않는다.

화면 문구는 `템플릿 선택`, `미리보기`, `빈 항목 채우기`, `선택 항목 교체`, `되돌리기`처럼 단순하게 한다.

## 4. 기능 B: 내 업무 모아보기

통합상황판에 `전체 현황 / 내 업무` 탭 또는 기존 디자인에 맞는 진입 버튼을 추가한다. 기존 통합상황판을 개인 화면으로 대체하지 않는다.

### 표시할 내용

- 나에게 배정된 미종결 고장.
- 내게 배정된 오늘 예정 정비.
- 예정일이 지났지만 완료되지 않은 내 정비: `기한 지남`으로 별도 표시.
- 내가 확인해야 할 지시사항.
- 각 영역의 건수·빈 상태·최근 갱신시각.

### 개인 범위와 권한

- `내게 배정된 고장`은 `assigned_to=currentUser.id`를 기준으로 한다. 팀에 배정된 작업은 보여줄 경우 `소속 반 업무`로 분리하며 개인 업무 수에 섞지 않는다.
- USER에게는 자신이 신고한 미종결 접수를 `내가 접수한 고장`으로 제공한다. 배정받은 작업이라고 잘못 표시하지 않는다.
- 정비는 기존 `assignee_id`를 기준으로 한다. 작성자·부서명 문자열을 담당자라고 추정하지 않는다.
- 지시사항은 나에게 직접 지정된 항목, 기존 정책상 내 부서에 적용되는 항목, 전체 공지 중 내가 확인하지 않은 항목으로 한정한다. 소속/부서의 신뢰할 매핑이 없으면 문구 유사도로 접근 권한을 넓히지 않는다.
- 지시의 `확인`과 업무 `완료`는 별개다. 만료·삭제된 지시, 이미 확인한 지시의 표시 정책을 명시한다.
- 기존에 허용된 지시 확인 권한은 유지하되, VIEWER에게 배정·정비 완료 등 업무 변경 권한을 주지 않는다.
- Main에서 현재 로그인 사용자로 조회 범위를 결정한다. renderer가 넘긴 임의 userId로 다른 사람의 업무를 조회할 수 없어야 한다.
- 건수와 목록은 같은 필터를 사용한다. 제한 목록이면 `총 N건 중 K건`을 표시한다.

### 상세 이동

- 고장·정비·지시사항 행을 누르면 기존 화면에서 해당 ID의 상세가 바로 열린다. 단순 메뉴 이동으로 끝내지 않는다.
- HashRouter와 기존 breadcrumb를 유지하고 URL query 등 기존 구조에 맞는 deep link를 사용한다.
- 검색·pagination 때문에 목록에 없는 항목도 ID로 권한 확인 후 상세 조회한다.
- 삭제·권한 변경된 항목은 안내 후 복귀한다. 상세를 닫을 때 내 업무 위치를 복원한다.
- 처리 완료·지시 확인 후 건수와 목록이 갱신된다. 늦게 도착한 이전 계정 요청을 표시하지 않는다. 로그아웃/계정 전환 시 개인 캐시를 비운다.
- 날짜는 Asia/Seoul 업무일 기준이다. 미래 정비를 오늘 예정 수에 섞지 않는다. 필요하면 별도 예정 목록으로 제공한다.

## 5. 기능 C: 정비 체크리스트

기존 정비 상세에 `점검 항목` 영역을 추가한다. 현재 상태 변경·결과 입력 화면 안에서 사용할 수 있게 한다.

### 기본 템플릿 예시

- 정기점검: 외관·전원·연결·기본 동작·결과 기록.
- 네트워크 점검: 전원·케이블·연결 상태·통신 시험·결과 기록.
- 통신장비 점검: 전원·연결부·송수신 상태·잡음 여부·결과 기록.
- 보안/프로그램 점검: 서비스 상태·로그 확인·설정 확인·동작 확인.

위 항목은 시연용 일반 점검 안내다. 실제 장비의 공인 정비절차 또는 자동 원격제어 기능으로 표현하지 않는다.

### 결과와 완료 조건

- 항목별 `미확인 / 정상 / 이상 / 해당 없음`, 메모, 확인자·시각을 저장한다.
- 필수 항목과 선택 항목을 구분한다.
- 필수 항목은 `정상` 또는 해당 항목에서 허용한 `해당 없음+사유`여야 완료 가능하다.
- 필수 항목의 `이상`은 해결하여 재확인하기 전 완료를 차단한다. 선택 항목의 이상은 조치 메모를 요구한다.
- `해당 없음`을 허용하지 않은 필수 항목에 임의로 N/A를 넣어 우회할 수 없어야 한다.
- 완료 전 누락·이상 항목 목록으로 이동할 수 있게 한다. UI 경고와 별개로 `maintenance:updateStatus`의 Main transaction에서 같은 조건을 강제한다.
- 기존 원인·상세 조치·결과·조치방식 입력도 계속 필수다. 체크리스트가 결과 입력을 대체하지 않는다.
- `5개 중 3개 점검`, `필수 1개 미완료`처럼 표시한다. 체크리스트 점검률과 기존 정비 진행률은 별개이며 자동으로 작업을 완료하지 않는다.
- 입력 저장 중 중복 조작과 오래된 화면의 덮어쓰기를 방지하고 실패 시 재시도할 입력을 보존한다.
- 완료된 작업은 조회 전용이다. 완료 후 체크 결과 수정으로 당시 근거가 바뀌지 않아야 한다.
- 체크 변경·초기화·템플릿 교체는 수행자와 주요 변경 이력을 남긴다. 진행 중 템플릿 교체는 체크 결과 소실 미리보기와 명시적 확인을 요구한다.

### 기존 작업 호환

- 신규 작업은 정비 유형에 맞는 템플릿을 미리 선택해 보여주고 저장 시 항목 snapshot을 만든다. 해당 유형 템플릿이 없으면 일반 점검을 선택하거나 체크리스트 없이 등록할 수 있다.
- 기존 작업에 체크리스트를 일괄 소급 적용하지 않는다. 미부착 작업은 기존 완료 방식이 유지된다.
- 권한 있는 담당자는 미완료 작업에 체크리스트를 명시적으로 추가할 수 있다.
- 원본 체크리스트 템플릿은 ADMIN만 관리한다. 개별 작업 결과는 기존 ADMIN/배정 MAINTAINER 권한으로 처리한다.
- 템플릿 수정·비활성화는 이미 생성된 작업의 항목·필수 여부·문구를 바꾸지 않는다.

## 6. 기능 D: 반복 정비 등록

정비관리의 기존 화면에 `반복 정비` 탭 또는 버튼을 추가한다. 복잡한 캘린더 편집기 없이도 아래 흐름이 가능해야 한다.

`반복 규칙 등록 → 다음 일정 미리보기 → 생성할 작업 선택 → 확정 생성 → 기존 정비 목록·캘린더·내 업무에서 처리`

### 규칙 입력

- 작업명, 정비 유형, 설명, 부서/체계, 우선순위, 담당자, 체크리스트 템플릿.
- 시작일, 선택적 종료일.
- 매주: 반복 간격 N주와 요일 1개 이상.
- 매월: 반복 간격 N개월과 기준 일자 1~31 또는 매월 마지막 날.
- 사용/일시중지.

단순한 날짜 반복만 지원한다. 공휴일·근무일 달력·복잡한 RRULE은 이번 범위에 추가하지 않는다.

### 날짜 정책

- Asia/Seoul의 날짜 값으로 계산하고 기기 timezone에 따라 하루씩 달라지지 않게 한다.
- 시작·종료일은 포함한다. 주 시작은 월요일이며 N주 간격은 시작일이 속한 주를 기준으로 고정한다. 시작일 이전의 같은 주 요일은 생성하지 않는다.
- 매월 31일인데 해당 월에 31일이 없으면 그 월 마지막 날을 사용한다. 다음 달에는 원래 31일 기준으로 복귀하여 28일로 계속 밀리지 않게 한다. `마지막 날`도 같은 명시적 정책을 사용한다.
- 기본 미리보기는 앞으로 30일. 범위 최대 90일, 한 번 생성 최대 100건으로 제한하고 초과 시 사용자에게 범위를 줄이도록 안내한다. 조용히 잘라서 전부라고 표시하지 않는다.
- 앱을 꺼 둔 기간의 작업을 시작 시 자동 소급 생성하지 않는다. 과거분은 명시적인 기간 선택·경고·미리보기·승인으로만 생성한다. 마감된 업무일의 생성은 기존 마감 정책을 따른다.

### 생성·중복·수정 정책

- 미리보기에서 예정일·담당자·유형·체크리스트·기존 생성 여부를 보여준다. 이 단계에서 업무 task는 저장하지 않는다.
- 실제 생성은 Main transaction에서 규칙 version·권한·기간·담당자·이미 생성된 occurrence를 다시 확인한다. renderer가 조작한 날짜·작업 수를 그대로 신뢰하지 않는다.
- `(반복 규칙 ID, 원래 발생 예정일)`에 DB unique 제약 또는 동등한 유일성을 둔다. task의 나중 변경된 예정일과 원래 발생일을 분리한다.
- 여러 번 클릭·재실행·중복 요청·앱 재시작에도 같은 회차를 다시 만들지 않는다. 기존 생성/취소 회차는 skip하고 생성/skip/실패 건수를 반환한다.
- 기존 생성된 회차를 취소했다고 자동 재생성하지 않는다. 이번 범위에서는 같은 회차 재생성 기능을 만들지 않는다.
- 규칙 수정은 앞으로 아직 생성하지 않은 작업에만 적용한다. 이미 생성한 task를 자동 변경·삭제하지 않는다. 같은 날짜를 규칙 version 변경만으로 중복 생성하지 않는다.
- 규칙 일시중지·삭제는 향후 생성만 막고 기존 task·체크 기록은 보존한다. 참조가 있으면 soft delete를 사용한다.
- 개별 발생 작업의 일정 변경·취소는 해당 작업만 바꾼다. UI에 `이번 작업에만 적용`을 표시한다.
- 규칙 수정/중지 후 오래된 미리보기의 확정 요청은 거부하고 다시 미리보게 한다.
- batch 실패는 원자적으로 rollback하며 유일성으로 확인된 기존 회차는 안전하게 skip한다.

### 담당자와 기존 업무 연계

현재 정비 생성 코드가 작성자를 `assignee_id`로 넣는지 먼저 확인하라. 반복 규칙에서 지정한 담당자가 생성자와 달라도 정확하게 배정되어야 한다.

- ADMIN은 유효하고 허용된 담당자를 선택할 수 있다.
- MAINTAINER는 자기 담당 규칙과 자기 작업만 생성·수정할 수 있다. 다른 사람 배정은 금지한다.
- 담당자 비활성화·권한 변경 시 생성 전에 알려주고 재지정을 요구한다. 생성자에게 조용히 바꾸지 않는다.
- 필요하면 기존 `maintenance:create`에 선택적 assigneeId를 추가하되 생략 시 이전 동작을 유지하고 Main에서 검증한다.
- 생성 작업은 기존 `maintenance_tasks`와 동일한 등록 경로·번호·이벤트·첨부·캘린더·체크리스트를 사용한다.
- 반복 규칙/미리보기를 task 수에 집계하지 않는다. 생성된 실제 task만 기존 통계에 들어간다. 일일 계획 건수는 기존 수동입력 정책을 존중하고 임의로 더해 중복 집계하지 않는다.

## 7. 기능 E: AI 입력 보완 도우미

고장 신규 접수·상세 AI 분석과 AI 지원의 고장 분석 카드에서, 입력 내용이 부족할 때 짧은 확인 질문으로 보완하도록 한다.

### 화면 흐름

1. 제목·내용 입력.
2. `입력 내용 점검` 또는 기존 분석 버튼 클릭.
3. 부족한 항목이 있을 때만 3~5개의 질문 표시.
4. 답변 또는 `확인하지 못함` 선택.
5. `보완 내용 반영` 미리보기.
6. 사용자 클릭으로 기존 AI 분석 실행.
7. 추천 근거·Provider·fallback 확인 후 기존 검토 반영.

### 질문과 사실 보호

- 기본 점검은 로컬 규칙이다. 시각, 범위, 오류/증상, 서비스 영향, 이미 수행한 조치 중 실제 누락된 것만 묻는다.
- 외부 LLM을 호출하지 않은 로컬 질문에는 `입력 점검 · 로컬`이라고 표시한다. 모델이 생성했다고 오해하게 만들지 않는다.
- 적용한 고장 템플릿의 질문/답변을 재사용하고 동일 질문을 반복하지 않는다.
- 내용이 충분하면 불필요한 설문 없이 기존 분석으로 이어진다. 모호한 내용은 경고하되 `현재 내용으로 분석`을 허용한다. 안전 관련 미확인 사항은 결과에 남긴다.
- 키워드 점검을 사실 확인·고장 진단·교정된 품질 점수로 과장하지 않는다.
- 답변을 바탕으로 부족한 업무정보를 보완할 뿐, 원인·정확한 발생시각·조치 성공 여부를 추측해 채우지 않는다.
- 질문 답변을 구조화하여 관리하고 반영 시 중복 문단을 생성하지 않는다. 사용자가 자유롭게 수정한 본문은 보호한다.
- 저장된 고장에 반영하려면 기존 수정 권한을 검사하고 변경 미리보기·명시적 저장·업무 이력을 남긴다.
- 분석 권한만 있고 접수 수정 권한이 없는 역할은 보완 답변을 분석용 임시 입력으로만 쓸 수 있게 하고 `분석에만 사용·접수 원문 미저장`을 표시한다. 이 기능 때문에 기존 수정 권한을 확대하지 않는다.
- AI 지원의 비저장 분석 입력은 세션 메모리에서만 관리한다. 계정 전환·로그아웃 시 지운다. 미요청 자동저장/localStorage 저장을 추가하지 않는다.
- 기존 고장/정비를 자동 생성하거나 담당자·긴급도·상태를 자동 변경하지 않는다.

### 기존 AI 연결

- 보완 결과를 기존 `ai:triageIncident`와 Provider 계층에 전달한다. 별도 API client를 renderer에 만들지 않는다.
- 템플릿·질문 입력 중 API 자동 호출, 자동 반복 분석, debounce 유료 호출을 추가하지 않는다.
- 외부 Provider 사용은 기존 활성화·동의·마스킹·Key 보호·timeout·retry·요청한도·Local fallback을 그대로 적용한다. 보완 답변도 동일 마스킹 경로를 통과한다.
- 중복 클릭 방지와 진행/실패 표시, 실패 시 입력 보존.
- 분석 중 입력이 바뀌면 응답을 당시 입력과 연결하고 `입력 변경 후 이전 결과`를 표시하거나 폐기한다. 오래된 답변을 최신 입력 결과로 적용하지 않는다.
- AI 결과는 항상 추천이며 기존 검토 후 반영 경로만 사용한다. SLA 결정적 계산은 유지한다.

## 8. DB·IPC·권한·구현 방식

필요한 최소 변경으로 기존 service/repository 구조를 따른다. AppService를 계속 늘리는 대신 템플릿·체크리스트·반복 일정 계산·내 업무 조회·입력 점검을 적절히 분리한다. 새 framework나 대형 추상화 계층은 필요 없다.

DB는 실행 시 현재 schema version을 확인한 additive migration으로 확장한다. 다음은 예시이며 기존에 같은 목적의 구조가 있으면 재사용한다:

- 고장 템플릿, 버전/질문 정의, 접수별 답변 snapshot.
- 정비 체크리스트 템플릿, task별 항목 snapshot/결과/이력.
- 반복 정비 규칙, 원래 발생일·task ID·생성 batch·규칙 version.
- `내 업무`는 기존 테이블 조회로 구현하며 중복 업무 테이블을 만들지 않는다.

요구사항:

- 기존 업무·사용자·설정·첨부·AI 이력 보존, migration 재실행 멱등성, seed idempotency, Drizzle/runtime schema 일치.
- FK·unique·index·parameterized SQL. 템플릿 비활성화/삭제로 과거 snapshot이 사라지지 않게 한다.
- 모든 신규 IPC 입력을 `src/shared/contracts.ts` Zod schema로 검증하고 출력 타입도 명확하게 한다.
- Main에서 로그인·역할·행 소유권·담당자·target 상태·길이·날짜·version을 검사한다. 클라이언트가 숨긴 버튼을 보안으로 간주하지 않는다.
- 새로 필요한 get-by-ID에도 기존 list와 동등한 조회 권한을 적용한다.
- ADMIN: 전역 템플릿 관리·규칙 관리·허용된 배정. MAINTAINER: 자기 작업 체크/자기 반복 규칙. OPERATOR/USER: 기존 접수 권한 유지. VIEWER: 업무 변경 금지. 지시 확인은 기존 확인 정책을 유지한다.
- 요청자가 모든 질문/체크 항목 ID를 임의로 보내도 실제 template/task 소속과 required 여부는 DB에서 검사한다.
- 중요한 변경과 반복 생성 결과는 기존 감사/업무 이벤트에 기록한다. 비밀번호/API Key/민감한 자유입력 원문을 로그에 넣지 않는다.
- 신규 저장 데이터는 기존 백업·복원 경로에 포함한다. Demo reset은 생성 소유권이 확인된 시연 데이터만 정리하고 사용자 템플릿·일정을 삭제하지 않는다.
- 오류는 이해 가능한 한국어로, 실패 후 입력은 유지한다. 비동기 응답이 unmount/계정 변경 후 화면에 섞이지 않게 한다.
- Electron `contextIsolation:true`, `nodeIntegration:false`, `sandbox:true` 유지.

## 9. UI 품질

- 기존 공용 Card, StatusChip, Button, Dialog, 입력 컴포넌트를 재사용한다.
- 새 화면마다 메뉴를 늘리지 말고 관련 업무 화면에 배치한다. 내 업무는 통합상황판, 템플릿은 접수, 체크리스트는 정비 상세, 반복 규칙은 정비관리, 보완 도우미는 분석 흐름에 넣는다.
- 입력 label·제목과 카드 상단의 간격을 확보하고 긴 제목·여러 질문에도 버튼이 잘리지 않게 한다.
- 1366×768과 1920×1080에서 modal 내부 스크롤, footer 버튼, 달력, 긴 텍스트, 표를 점검한다.
- 키보드 focus, label, 필수/선택 표시, loading, 빈 상태, 오류, 성공 안내를 제공한다. 색상만으로 완료·이상을 구분하지 않는다.
- 기존 저장 버튼이 뜻하지 않게 템플릿 적용·질문 응답만으로 눌리거나 기존 업무를 변경하지 않게 한다.

## 10. 필수 테스트와 실제 검증

테스트는 합성 fixture·격리된 profile/DB를 사용한다. 실제 사용자 DB를 초기화하지 않는다. 자동 테스트에서 실제 OpenAI/Claude API를 호출하지 않는다.

단위/통합:

1. 고장 템플릿의 빈 필드 적용·충돌 확인·수정 보존·해제·되돌리기·snapshot 유지·seed 재실행.
2. 템플릿 미사용 기존 접수, 미확인 답변, 긴급 접수 우회 없는 기본 계약, 예시가 사실로 자동 저장되지 않음.
3. 내 업무의 사용자별 고장/정비/지시 필터·count·기한·만료·KST 자정·로그아웃 캐시.
4. 상세 deep link·검색 밖 ID·삭제/권한 없는 ID·직접 IPC 접근.
5. 체크리스트 필수 누락/이상/N/A 사유 검사, 정상 완료, 기존 미부착 작업 완료, 완료 후 변경 차단.
6. 체크 템플릿 변경이 기존 task에 미치는 영향 없음, 타인 task의 체크 ID 조작 거부.
7. 매주/N주·다중 요일·월간/N개월·31일·윤년·월말·시작/종료 경계·기기 timezone 차이.
8. 반복 미리보기 DB 미변경, batch 생성, 재요청/중복/재시작 멱등성, 취소 회차 중복 방지, 개별 일정 변경 후 원래 회차 unique 유지.
9. 규칙 수정/일시중지·비활성 담당자·stale 미리보기·위조 발생일·생성 상한·transaction rollback.
10. ADMIN이 다른 유효 담당자로 생성, MAINTAINER 타인 배정 차단, 기존 일반 정비 생성 호환.
11. 보완 질문의 누락 탐지·중복 질문 제거·미확인·건너뛰기·답변 중복 반영 방지·접수 수정 권한.
12. 입력 점검만 수행했을 때 외부 API 0회, 기존 AI 네 Provider mock/LOCAL 경로와 실패 fallback, 마스킹·stale 결과 처리.
13. 이전 DB 업그레이드·migration 재실행·기존 row 보존·신규 row 백업/격리 복원.

E2E는 최소 다음을 실제 버튼·DB로 검증한다:

- 템플릿 선택→질문 답변→사용자 수정→접수→재실행 후 기록 유지.
- 기존 입력이 있는 상태에서 다른 템플릿 적용·취소·내용 보존.
- 서로 다른 두 계정의 내 업무 분리→상세 열기→업무 처리/지시 확인→건수 갱신.
- 체크리스트 일부 입력 저장→앱 재실행→복원→필수 누락 상태 완료 차단→모두 점검+기존 결과 입력→완료.
- 반복 규칙→미리보기→담당자 확인→선택 생성→목록/캘린더/내 업무에서 동일 task 확인→재생성 0건.
- 규칙 변경·일시중지 시 기존 생성 작업 보존.
- 부족한 고장 입력→보완→수정→기존 AI 분석→검토 후 반영.
- 입력 점검 중 API 무호출, 외부 AI mock 오류 시 LOCAL 결과와 입력 보존.
- 기존 접수·정비·등록 신청·역할·첨부·마감·보고서 회귀.
- 두 해상도 screenshots를 저장하고 실제로 열어 겹침·잘림·여백을 확인.

기존 필수 명령:

```text
pnpm install --frozen-lockfile
pnpm typecheck
pnpm lint
pnpm test
pnpm build
pnpm test:e2e
pnpm test:e2e:roles
pnpm test:e2e:signup
pnpm test:e2e:operations
pnpm test:e2e:visual
pnpm test:e2e:external-ai
pnpm dist:win
```

신규 E2E를 `pnpm test:e2e:usability` 등 명확한 script로 추가해 실행한다. 기존 script의 검증 범위를 줄여 통과시키지 않는다.

최종 Windows `release/win-unpacked/OMNIS.exe`에서 packaged smoke·operations·신규 5기능 E2E를 수행한다. 설치 파일 경로·크기·SHA-256·서명 여부를 기록한다. 실행 가능한 unpacked 앱 테스트와 clean PC 설치 테스트를 구분한다.

macOS 호환 코드를 유지하고 플랫폼별 파일 경로·날짜·native module 차이를 확인한다. Mac 또는 승인된 CI가 없으면 macOS 실실행 미검증으로 기록한다. Windows 통과를 macOS 검증으로 대체하지 않는다. 실제 API live call도 opt-in 별도 승인 전 수행하지 않는다.

## 11. 문서와 완료 보고

README.md, PROJECT_STATUS.md, 관련 AI/DB/IPC 문서, 요구사항 추적표·시연 가이드를 현재 변경에 맞게 갱신한다. 새로 `docs/FIVE_FEATURES_USER_GUIDE.md`를 만들어 다음을 설명한다:

- 기능별 위치와 클릭 순서.
- 기존 방식과 새 방식의 차이.
- 템플릿 적용/되돌리기와 미확인 답변.
- 내 업무의 개인/소속 반/내 접수 구분.
- 체크리스트의 완료 조건과 N/A 정책.
- 반복 일정의 월말·중복·수정·중지 정책.
- 입력 점검과 실제 AI 분석의 호출·비용 차이.
- 권한·오류 복구·저장 위치·오프라인 동작.

5~7분 안에 아래 시나리오를 시연할 수 있게 한다:

1. 템플릿으로 접수하고 부족한 내용을 보완.
2. 기존 AI 분석 결과를 검토한 후 배정.
3. 담당자 계정의 내 업무에서 해당 고장 상세 열기.
4. 반복 정비 다음 일정을 미리보고 담당자에게 생성.
5. 내 정비에서 체크리스트 입력 후 기존 결과를 작성하여 완료.
6. 같은 반복 기간을 다시 생성해 중복 0건 확인.

완료 판단:

- 5개 기능이 실제 DB·IPC·권한·UI에 연결되고 재시작 후 필요한 데이터가 유지됨.
- 기존 자유 접수·정비·AI·첨부·마감·보고서·백업에 회귀 없음.
- 사용자 작성 내용 유실, 타인 업무 노출, 필수 체크 우회, 반복 작업 중복 없음.
- LOCAL 환경에서 신규 실용 기능 전부 사용 가능.
- 테스트·Windows 패키징·packaged E2E의 실제 결과와 미검증 항목을 기록.
- 합성자료만 사용한 사용설명서와 시연 시나리오 제공.

적절한 단위로 로컬 commit하고 staging을 검토한다. 이번 범위와 무관한 파일·생성물·비밀정보를 포함하지 않는다.

최종 보고에는 ① 변경 기능 ② 화면 사용 순서 ③ 기존 기능 호환·데이터 보존 ④ 실제 테스트 명령/결과 ⑤ 설치 파일 경로/크기/hash/서명 ⑥ branch/commit ⑦ macOS/live API/clean PC 등 미검증 항목을 포함한다. 실행하지 않은 항목을 통과했다고 표현하지 않는다.

이제 현재 저장소를 조사하고, 위 5개 기능의 구현·검증·패키징·문서화까지 진행하라.
