## 3. 사실·구현·검증 경계 확정

먼저 기능별로 `구현 완료 / 부분 구현 / 제안 / 검증 미실시`를 판정한 근거표를 만든다. 각 행에는 화면·IPC·서비스·DB·시험 또는 기록의 연결 근거를 적는다.

특히 다음 구분을 지킨다.

- 실제 스택은 Electron/React/TypeScript/MUI, Main·Preload·검증된 IPC, SQLite/better-sqlite3/Drizzle 등을 코드로 확인해 쓴다. PDF의 Spring Boot·MySQL은 권장 스택이다. 사용하지 않는 스택을 적용했다고 쓰지 않는다. 독립 PC 운용과 별도 서버 설치 최소화 관점에서 실제 선택 이유를 설명한다.
- 현재 기본 운용은 로컬 PC의 앱·DB다. 동일 PC의 화면/DB 갱신을 실제 군 내부망 다중 PC 실시간 공유나 장비 자동 수집으로 확대 해석하지 않는다.
- 상황경보와 GPS 전파교란 등의 입력·변경 기능을 실제 센서 탐지·실시간 전파 감시로 표현하지 않는다.
- 요청부서와 조치부서, 근무 명부와 실제 병력 현황, 사용자 가입 승인과 정비 요청 승인, 고장 결과 검증과 장비 실물 검증은 서로 구분한다. 별도 정비 승인·병력 집계 등 요구사항이 부분 충족이면 그대로 적는다.
- Local Rule은 결정적 규칙이며 생성형 LLM이 아니다. Ollama 연동 코드, Ollama 프로그램 설치, 모델 다운로드, 서버 기동, 실제 모델 응답 검증은 각각 다른 상태다.
- OpenAI/Claude 연동 구현·mock 시험과 실제 유료 API 호출 성공을 구분한다. 실제 API 키·결제·모델 접근·네트워크 상태를 확인하지 않고 실시간 AI 운용 성공으로 쓰지 않는다.
- 유사 고장은 현재의 후보 검색/재정렬 방식으로 설명한다. RAG·임베딩·벡터 DB·문서 학습을 구현했다고 쓰지 않는다.
- SLA 위험은 앱의 설명 가능한 규칙 계산이며 LLM이 산출한 실측 확률이 아니다.
- 데이터 최소화·패턴 마스킹·OS 암호화는 구현된 보호수단이다. 완전한 개인정보 비식별화·군 보안 인증·운영 승인 획득으로 표현하지 않는다.
- Windows 설치본 생성/패키징 앱 시험, 실제 설치 업그레이드, 깨끗한 신규 PC 설치, macOS 구성/CI/실기기 시험, 전자서명·공증은 따로 판정한다.
- 출처가 있는 공개 부대명과 부서명도 전수 최신 공식 편제 확인으로 표현하지 않는다. 담당자 명부는 가상 데이터임을 명확히 한다.

### 2. 체계 개념

가. 체계 소개에는 목적·대상 역할·운용 환경·경계, 실제 개발스택, 데이터 저장·백업·복구·기존 데이터 보존, 설치 및 독립 PC 실행을 적는다.

실제 아키텍처 그림을 포함한다: 사용자 → Renderer → Preload/contextBridge → Zod 검증 IPC → Main 권한/업무 서비스 → 로컬 SQLite/첨부/백업. LOCAL, 별도 설치형 Ollama, 동의 후 선택형 외부 HTTPS AI 경계를 표시한다. 실제 없는 AWS·웹 서버·클라우드 DB·Nginx·RAG 구성요소는 넣지 않는다. 기존 docs/architecture 도면은 현행과 대조해 사용한다.

나. 체계 주요기능에는 실제 확인된 다음 기능을 빠짐없이 분류한다.
- 통합상황판의 집계·상세 이동, 체계 운용 상태/이력·상황경보 입력/수정.
- 고장 접수·분류·요청부서/조치부서 분리·미지정·부서/담당자 지정, 원격/현장·결과·검증·종결, 긴급 선조치 사후기록.
- 정비 등록·예정일·우선순위·담당·진행/완료·캘린더·이력과 구현된 알림.
- 계획/비계획 작업판·정합성 검사·일일 마감·인수인계.
- 근무 편성·부대별 가상 담당자 명부·다중 담당자·지시사항 확인/이행.
- 일일/주간 보고·CSV/PDF, 역할별 권한·가입 승인·감사·백업·역할별 매뉴얼 다운로드.

각 기능은 목적→수행 역할→입력→처리/판단→출력→예외/통제→현행 업무 개선점 순으로 설명한다. 화면 이름을 단순 나열하지 않는다. 기본 요구, 차별 기능, 향후 제안을 중복 계산하지 않는다.

다. 운용개념 및 운용 시나리오는 최소 다음을 단계별로 작성한다.
1) 일반 고장 접수부터 검증·종결까지: 실제 입력 예시와 기록·담당 역할의 연결.

3) 정기/비계획 정비와 08:30·16:00 작업 대조, 미완료 인계.
4) 선택형 AI 분석→근거/질문 확인→사람 검토→반영, 실패 시 Local Rule 대체.

역할별 수영레인 형태의 업무 흐름도 또는 역할/행위/화면/데이터/검증 조건 표를 사용한다. 실제 기기 조작·자동 서비스 복구를 수행한 것처럼 쓰지 않는다.

### 3. 추가기능 구현

아래는 현재 코드를 검토해 기본 요구와 구분한 뒤 서술한다. 구현 근거가 있는 항목만 완료로 쓴다.
- 고장 접수 템플릿: 예시 증상·필수 질문 제공, 저장 전 사용자 수정.
- 내 업무 모아보기: 배정 고장·오늘 정비·확인할 지시사항과 상세 이동.
- 정비 체크리스트: 작업별 항목·저장·필수 미완료 검증.
- 반복 정비: 주/월 규칙·생성 전 미리보기·중복 회차 방지·날짜 예외.
- 로컬 입력 보완: 누락 질문·답변 보존·기존 분류로 연결.
- 추가로 구현된 첨부자료 검증, 설명 가능한 SLA, AI 이력/검토 반영, 부대별 명부, 역할별 매뉴얼, 업무 대조/인수인계 등의 차별성을 중복 없이 정리.

각 추가기능을 현장 문제→실제 동작→사용 단계→구현/검증 증거→다른 업무로의 확장성으로 연결한다. 제목만 멋있게 쓰거나 미래 계획을 이미 구현한 것으로 세지 않는다.

### 4. AI 활용도 — 개발 과정과 앱 기능을 분리

PDF 6쪽의 AI 활용도 30점은 다음 개발 과정 증빙이다.
1) 요구사항·조건이 포함된 구체적 프롬프트 작성: 10점.
2) AI 결과 확인 및 프롬프트 수정·보완: 10점.
3) 생성 결과 검토·수정 후 프로그램에 적절히 반영: 10점.

이를 앱에 LLM API가 탑재되었는지만 설명하는 내용으로 대체하지 않는다. 가. 활용 AI체계는 다음 두 층으로 분리한다.
- 개발 지원: 실제 근거가 있는 Codex/Claude 등 도구로 요구 분석·설계·구현·오류 수정·테스트를 지원한 과정.
- 운용 중 업무지원: LOCAL/Ollama/OpenAI/Anthropic, 구조화 분류·질문·요약·후보 재정렬·검토 후 반영·실행 이력. 연결 코드를 만든 사실과 실제 모델 호출 검증 상태를 구분한다.

나. AI 활용 SW 구현정도는 전체 SW 완성도, AI 협업개발 활용 비율, 런타임 AI 기능 구현률을 혼동하지 않는다. 원문 용례·작성자 의도를 설명하고 기능 단위 등의 산정 범위·분자·분모·중복 방지 기준을 명시한다. 확인 근거 없이 90%·100%를 만들지 않는다. 증빙이 부족하면 본문에 산정 보류와 확인 사유를 기재하고 작성자 확인표를 제공한다.

원문 표 열을 유지한다: `주요/추가기능 | 바이브 코딩 사용 | 입력 프롬프트 | 활용 소스코드`. 캡처 증빙 영역의 셀 병합은 원본 이미지와 대조해 확정한다.
- 기능별 O/X는 실제 개발 기록이 확인되는 경우만 표시한다. Git 작성자·코드 줄 수만으로 AI 작성 여부를 단정하지 않는다.
- PDF 8쪽은 캡처 증빙을 요구하며 소스코드 직접 입력을 금지한다. 표의 증빙 칸에 원문 프롬프트 화면과 관련 구현 파일의 실제 화면 캡처·증빙 번호를 넣는다. 코드를 긴 텍스트로 복사해 넣지 않는다.
- 표의 행은 본문 2-나/3 기능 번호와 연결한다. 캡처가 많으면 셀에는 축소 이미지와 증빙 번호를 넣고 부록에서 읽을 수 있는 크기로 제공한다.
- 입력 프롬프트→첫 결과의 한계→보완 요청→수정 코드/화면→실제 검증을 비교할 수 있게 한다. 실제 저장 흐름·부서 조회·근무 명부·오늘 배지 수정 등 근거가 확보된 사례를 우선 검토한다.
- 없는 AI 대화나 편집기 화면을 만들어 실제 기록처럼 사용하지 않는다. 재구성 요약은 재구성이라고 표시한다. 원문 캡처가 없으면 누락을 밝히고 대체 근거·작성자 확인 필요 항목을 구분한다.
- 캡처에 API Key, 인증정보, 개인정보·군사자료가 보이지 않게 한다. 허용되지 않은 개인 대화·세션·비밀 파일을 임의로 수집하지 않는다.

### 5. 타 체계 연동방안(제안)

현재 구현된 내보내기·파일 입출력과 아직 제안 단계인 업무체계 연동을 구분한다. 실제 AFCCS·DELIIS·내부망·인사/자산 체계에 연결한 것으로 쓰지 않는다.

제안에는 대상 업무 데이터 범주, 입력/출력 경계, 일반화된 CSV 또는 승인된 인터페이스 방식, 필드 매핑, 식별자/중복 검증, 권한·보안 승인, 미리보기·검토 후 반영, 오류 격리·감사·rollback, 단계적 검증 방법을 포함한다. 실제 내부 API 규격·주소·기밀 데이터는 추정하지 않는다.

개발 산출물의 군 내부망 반입·실무 사용 여부는 PDF 보안대책 및 승인 절차와 별도로 확인해야 한다. 확장 설계 가능성을 곧바로 승인·실연동 완료로 표현하지 않는다.

## 5. 평가 기준별 증빙 연결

아래 배점을 원문 6쪽과 재대조해 별도 대응표를 만든다. 공식 평가 점수나 과거 자체 예상점수를 확정 점수로 사용하지 않는다.
- 완성도 50: 실제 업무 절차 기반 15, 군 내 적용/운용 가능 구성 15, 주요 요구기능 정상 구현 10, 사용자 친화성·사용성/안정성 10.
- AI 활용도 30: 구체 프롬프트 10, 결과 확인·프롬프트 보완 10, 생성 결과 검토·수정·프로그램 반영 10.
- 차별성 15: 요구기능 외 추가 구현 10, 타 업무 확대·지속 활용 5.

부록에는 15분 시연 동선을 넣는다. 원문 5~6쪽에 지정된 2-나·2-다·3번을 중심으로 화면·행위·설명·예상 결과·소요시간을 연결하고 전체가 15분 이내인지 확인한다. 미실시 리허설은 실시했다고 쓰지 않는다. 예비 질의응답에는 로컬 앱/API 경계, 규칙과 LLM 차이, 실제 데이터 전송 범위, 권한·보안, 데이터 보존, 미구현 연동, AI 개발 기여 근거를 포함한다.

## 6. 보안·가상 데이터·캡처

PDF 3·5·7쪽의 보안대책을 정확히 반영한다. 실제 군사자료·실부대 운용 상태·개인정보·인증정보·실제 병력/군번·장비 식별값·망 구성·IP·위치 등은 문서·시험 입력·캡처에 넣지 않는다.

기존 앱에 공개 실부대명 카탈로그 등이 있더라도 제출 캡처는 별도 격리된 시연 DB에서 `가상 A조직`, `체계1`, `장비A`, `담당자 가` 같은 임의 값으로 구성한다. 실제 사용자 DB를 수정·초기화하지 않는다. 가명화가 필요한 값은 증빙 번호의 연결 관계만 유지한다. 산출물의 최종 보안 적합성은 담당자의 확인 대상으로 남기며 인증 완료로 쓰지 않는다.

첨부·AI 화면 등은 최신 앱의 실제 화면을 촬영한다. 원문 PDF의 사례 이미지를 우리 프로그램 실화면으로 사용하지 않는다. 새로 그린 개념도·재구성 자료는 실제 화면과 구분한다. 모든 그림에 제목·무엇을 증명하는지·자료 성격(가상/재구성)·근거를 붙인다.

외부 API Key를 요구하거나 임의로 찾아 읽지 않는다. 실제 API 호출, API 결제, Ollama 설치·모델 다운로드는 문서 작성의 선행조건으로 삼지 않는다. 미검증이면 그 상태를 기재하고 별도 시험 계획을 제시한다.

## 7. 문장·시각·편집 품질

공식 기술서에 맞는 차분한 흑백 중심 서식으로 만들고 제목/표 강조색만 절제해 사용한다. 홍보 문구보다 업무 절차와 판단 근거를 우선한다. 약어는 첫 등장에 뜻을 설명하며 Source/IPC/Provider 등은 필요한 범위에서만 병기한다.

원본 양식의 제목·인적사항 표·번호·들여쓰기·표 열을 우선 재현한다. 스캔의 기울어짐과 오염을 따라 만들지 않는다. 용지·여백·글꼴·줄간격은 원문 관찰과 읽기성을 기준으로 정하고 본문·표·캡션에 일관되게 적용한다. PDF에 없는 강제 서식 규정을 만들어 적용했다고 주장하지 않는다.

본문과 표는 편집 가능한 실제 글자·문단·표로 작성한다. 페이지 전체를 이미지로 붙여 편집 문서처럼 만들지 않는다. 이미지는 증빙 캡처·구성도에 사용하고, 구성도의 SVG 등 편집 원본도 보존한다. 한글 글꼴 깨짐·잘린 표·고아 제목·잘못된 번호·과한 여백·작은 캡처·넘치는 셀을 제거한다. 표 행의 페이지 분할과 긴 표의 머리행 반복도 확인한다.

기술서는 코드 설명서나 화면 사용법만의 나열이 되어서는 안 된다. 왜 필요한지, 누가 어떤 입력으로 어떻게 판단·처리하고 어떤 결과·책임 기록이 남는지를 일관된 운영 이야기로 설명한다.

## 8. HWP·DOCX·PDF 실제 생성

새로운 출력 폴더를 사용한다: `output/operation-concept/YYYYMMDD-HHmm/`. 동일 폴더가 있으면 원본을 덮어쓰지 말고 새 폴더를 만든다. 날짜와 문서 기준 시각은 Asia/Seoul을 사용한다.

필수 최종 산출물:
- `OMNIS_운용개념기술서_제출본.hwp`
- `OMNIS_운용개념기술서_제출본.docx`
- `OMNIS_운용개념기술서_제출본.pdf`

세 파일은 동일한 본문·표·그림·주요 번호를 포함해야 한다. 하나의 편집 원본에서 파생해 내용 차이를 최소화한다. 글꼴 차이로 페이지 수가 달라지면 조정·확인하고 차이를 기록한다.

로컬 Word·한글 실행 및 지원되는 자동화/변환 기능을 먼저 확인한다. 현재 사전 확인에서는 `HWPFrame.HwpObject`와 `Word.Application` 등록이 보였지만, 이는 실제 저장 성공 증거가 아니다. 실행 환경에서 다시 확인하고 실제 열기·저장을 검증한다.

DOCX는 실제 OOXML 편집 문서로 생성한다. HWP는 한글이 지원하는 경로로 DOCX를 열어 저장하거나 실제 HWP 문서를 작성한다. 지원되지 않는 자동화 API나 보안 우회는 추정해 사용하지 않는다. 권한 문제가 있으면 정상 승인 경로 또는 제공되는 문서/UI 도구를 사용한다.

확장자 변경은 변환이 아니다. DOCX/PDF/HWPX를 .hwp로 이름만 바꿔 제출하지 않는다. HWPX는 실제 .hwp 요청의 자동 대체품이 아니다.

HWP 저장이 불가능한 경우, 가능한 DOCX/PDF 및 원본은 완성·보존하고 정확한 장애와 필요한 도구/승인을 보고한다. 세 파일이 모두 생성·검증되지 않았는데 최종 완료라고 쓰지 않는다.

PDF는 최종 제출 HWP를 한글에서 PDF로 내보낸 결과를 우선한다. DOCX 기반 PDF와 최종 HWP가 서로 달라지는 상태를 방치하지 않는다. 필요하면 문서별 렌더링을 비교해 내용·표·캡션 일치를 검증한다.

## 9. 검증·근거 패키지

- 원본 PDF 7~8쪽 항목·표·순서의 누락 여부를 체크한다.
- 3·5쪽의 모든 주요 요구사항을 구현 근거/부분 충족/제안/확인 필요로 매핑한다.
- 6쪽 평가 항목과 본문·증빙의 연결을 확인한다.
- 주요 기능 설명을 현재 코드·화면과 대조한다. 오래된 PROJECT_STATUS의 예상 점수나 이전 버전 검증을 최신 근거로 대체하지 않는다.
- 필요한 앱 시험만 격리된 가상 프로필에서 수행하고 원본 사용자 DB·운영 설정·설치 앱을 건드리지 않는다. 현재 시험이 필요한 경우 실제 실행 결과를 기록하며 과거 기록 재인용은 기준일을 적는다.
- 한글과 Word에서 실제 다시 열기, PDF 내보내기, 전체 페이지 렌더링·육안 확인을 수행한다. 자동 텍스트 추출만으로 레이아웃 검증을 대신하지 않는다.
- HWP는 실제 형식/내부 식별 정보와 한글 재열기를 확인한다. HWP 5 형식이면 FileHeader의 HWP 식별값과 DocInfo/BodyText 등 해당 구조도 확인하며, 일반 OLE 파일이거나 확장자만 .hwp인 것을 정상 HWP로 판정하지 않는다. DOCX는 OOXML 구조와 편집 가능한 문단·표, PDF는 유효성·한글 표시·페이지/그림 상태를 확인한다.
- 세 문서의 제목·원문 항목·표·주요 수치·그림 번호·캡션이 일치하는지 검증한다. 변환 과정에서 손실된 항목은 수정한다.
- 전체 페이지를 확인해 겹침/잘림/깨진 글꼴/이미지 해상도/불필요한 빈 페이지 문제를 없앤다. 최종 저장 후 최신 출력본을 다시 검증한다.

부수 자료는 `evidence/` 등에 정리한다.
`양식_대응표`, `요구사항_구현근거표`, `평가항목_증빙표`, `작성자_확인사항`, `검증결과`, 캡처/도식 원본, 재생성 소스, 최종 파일명·크기·SHA-256 목록. 부수 자료를 필수 3종 대신 제출하지 않는다.

## 10. 실행 순서·완료 보고

1. 원본 PDF 및 최신 프로젝트 근거 조사, 사실/가정/미확인 목록 작성.
2. 원양식 구조와 평가 대응 확정, 보안 처리한 증빙 수집.
3. 동일 편집 원본으로 상세 본문·표·도식 작성.
4. DOCX·HWP·PDF 실제 생성 및 전체 렌더 검증.
5. 누락·불일치·서식 문제 수정 후 최종 파일 재열기/최종 QA.
6. 필수 3종과 부수 자료의 경로·검증 결과를 보고.

인적사항 공란처럼 자료가 없는 부분은 임의로 채우지 말고 확인사항으로 남긴다. 원문이 이미 정한 목차·평가 배점·절차를 사용자에게 다시 결정해 달라고 묻지 않는다. 핵심 자료가 실제로 없거나 승인이 필요한 외부 행위만 간결하게 질문하고, 독립적으로 가능한 작업은 계속한다.

최종 보고에는 HWP/DOCX/PDF 클릭 가능한 링크, 각 파일 페이지 수·크기·SHA-256, 7~8쪽 양식 대응 요약, 실제 검증 방법과 결과, 미확인 사실·인적사항·AI 기여 비율·live API 여부, 제출 전 작성자/보안담당 최종 확인사항을 포함한다. 최고점 보장·공식 승인·실운용 완료라는 표현 대신 확인된 근거를 제시하라.
