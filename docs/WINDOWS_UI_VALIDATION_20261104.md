# Windows 화면·배율 검증 — OMNIS 1.1.11

검증일: 2026-11-04 KST. 대상은 실제 Windows x64 PC에 설치한 앱입니다.

## 이전 검증과 추가 검증의 구분

1.1.10 설치 검증은 주요 기능 E2E 13종과 일부 화면 크기를 대상으로 했습니다. 당시 모든 화면을 직접 확인한 것은 아니며, 직접 본 대표 캡처는 통합상황판 2개 크기였습니다. 이 기록을 전체 화면 무결성 검증으로 해석하면 안 됩니다.

추가 검사에서 1920×1080 디스플레이의 150% 배율을 앱 실행 옵션으로 재현했을 때 최초 창이 작업 영역을 벗어나는 문제를 확인했습니다. 이 문제는 1.1.11에서 수정했습니다.

## 확인한 문제와 수정

- 원인: 최초 창 1600×950, 최소 창 1366×768이 고정돼 있었음.
- 150% 재현 시 작업 영역: 논리 픽셀 1280×688. 기존 최초 창은 1366×768이어서 오른쪽과 아래쪽이 모니터 밖으로 나갔음.
- 수정: Electron `screen.workArea`를 기준으로 최초 위치·크기와 최소 크기를 조절. 다른 화면으로 이동하거나 화면 배율·작업 영역이 바뀌면 최소 크기와 과도하게 큰 창을 다시 조절.
- 수정 후 최초 창 1280×688, 내용 영역 1270×662로 작업 영역 안에 들어옴. 100%의 기존 1600×950 창은 유지됨.
- 앱 메뉴·업무 데이터 계약과 Renderer 디자인은 변경하지 않음.

변경 파일: `src/main/index.ts`, `src/main/windowBounds.ts`, `package.json`과 회귀 검사 파일. 기준 커밋 `5cc22ae5237b0fba39c063b578913107dea3283d`에 `codex/windows-display-layout` 작업 트리 변경을 더한 빌드입니다. 설치 파일을 생성할 당시에는 미커밋 상태였으며, 이후 소스·검사·문서를 Git으로 전달합니다. 빌드에 사용한 파일 사본·SHA-256은 `release/windows-layout-1.1.11/source/` 및 `verification-summary.json`에 보관합니다. 전달 커밋과 빌드 사본의 동일성은 파일 해시로 확인할 수 있습니다.

## 화면 검사 범위

최종 99개 화면 상태, 중복을 제외한 387개 크기 조합. 재시도를 포함한 기본 캡처는 412장이고 긴 화면의 아래쪽 캡처는 별도입니다.

- 관리자 화면·팝업: 1268×662, 1280×720, 1366×768, 1536×864, 1920×1080.
- OPERATOR·MAINTAINER·USER·VIEWER의 실제 표시 메뉴: 1268×662와 1920×1080. ADMIN을 포함한 총 5개 역할.
- 실제 설치본의 전체 라우트: 통합상황판, 내 업무, 운영현황, 고장관리, 정비관리, 통제·일일마감, 근무·지시사항, AI 지원, 보고서·통계, 사용자 매뉴얼, 관리자센터, 시스템관리, 기존 사용자 신청현황 경로.
- 하위 탭: 정비 목록·캘린더·배정 고장, 통제 5개 탭, 근무·지시사항, 일일·주간 보고서, 시스템 5개 탭, 관리자센터 7개 영역과 조직 설정 하위 탭.
- 주요 팝업: 사용자 등록, 체계·고장·정비·근무·지시·경보 등록, 반복 정비 목록·규칙 등록, 체계·고장·정비 상세, 템플릿 수정, 조치부서 추가, AI 입력 보완·결과·실행 이력, 비밀번호 변경, 개인 알림함, 사용자 상세·권한 변경·변경 이력, 신청 승인·반려·상세, 상황경보 상세.
- Provider UI: LOCAL과 OPENAI·ANTHROPIC·OLLAMA 선택 상태. 설정을 저장하거나 실제 외부 API를 호출하지 않음.

자동 검사 결과: 문서 가로 넘침 0, 팝업 화면 경계 초과 0, 팝업 본문 가로 넘침 0, 검사 대상 조작부의 숨김 영역 가림 0, Renderer 예외 0.

1268×662의 99개 대표 상태를 모은 17개 컨택트 시트를 직접 검토했습니다. 실제 150% 최초 창과 시스템 설정·고장 상세의 아래쪽 캡처도 원본 해상도로 확인했습니다. 387개 조합을 모두 원본 크기로 하나씩 육안 판독했다는 뜻은 아닙니다.

긴 목록·설정 페이지·캘린더는 세로 스크롤, 넓은 표는 표 내부 가로 스크롤, AI 긴 결과는 카드 내부 스크롤을 사용합니다. 작은 창에서 본문 일부가 첫 화면 아래에 있는 경우는 스크롤로 접근할 수 있는지와 영구적으로 가려지는 경우를 구분했습니다.

## 배율 및 기능 회귀 결과

Windows 설정을 직접 바꾸지 않고 Chromium/Electron의 `--force-device-scale-factor=1`, `1.25`, `1.5`로 배율을 재현했습니다. 각 배율의 `screen.scaleFactor`, 작업 영역, 최초·최대화 창 경계와 논리 viewport를 기록했습니다. 세 배율에서 창 내용이 작업 영역 안에 들어오고 페이지 가로 넘침이 없는 것을 확인했습니다.

- 타입 검사·ESLint·Electron/React 빌드 통과.
- 전체 단위·통합 테스트 160/160 통과. 창 배치 회귀 테스트 5개 포함.
- 1.1.11 EXE 실제 설치 종료 코드 0, 실행 파일·app.asar·seed DB·매뉴얼 5종 설치 전후 해시 일치.
- 설치본 `smoke`, `roles`, `operations-flow` 재검사 통과: 저장·재실행·CRUD·PDF·백업·권한·업무 흐름.
- 실제 사용자 DB의 최초 검증 전후 SHA-256 일치. 가상 프로필만 사용.

최초 화면 검사의 잘못된 버튼명 2곳과 변경할 역할을 고르기 전 비활성화된 버튼을 누르던 검사 절차 1곳은 검사 스크립트에서 보완하고 재실행했습니다. 이를 앱 오류로 집계하지 않았으며, 원래 실행 로그의 미완료 기록도 보존합니다.
